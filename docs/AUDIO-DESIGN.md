# 音频方案（设计稿，未实现）

> 现状：**看一阵完全没有音频**。只处理窗口像素 + OCR。
> 这份文档把"以后要接声音"需要决定的事写下来，免得重新调研。

## 为什么现在没有

看一阵的输入是**窗口像素流**，没有音轨。要拿声音得单独建一条采集链路，和"锁窗口"的语义也不完全一致（音频是全局/按应用的，不是按窗口的）。

## 三条可行路径

| 路径 | 能抓什么 | 系统要求 | 代价 |
|---|---|---|---|
| **ScreenCaptureKit（音频）** | 显示器/系统的声音 | macOS 13+ | 需要"屏幕录制"权限（已有）；要写 Swift 采集流，格式转换 |
| **CoreAudio 进程 tap** | **指定应用**的声音（最贴合"这个窗口在放什么"） | macOS 14.2+ | 需要新权限（音频捕获）；API 较新，兼容性风险 |
| **虚拟声卡（BlackHole 等）** | 系统声音混音 | 用户要装驱动 | 最通用，但要用户装第三方驱动，门槛高 |

看一阵如果要"听这个视频的声音"，语义上 **CoreAudio 进程 tap** 最准确（按应用抓）；退一步用 ScreenCaptureKit 的系统音频也行。

## 转写（ASR）怎么选

| 方案 | 优点 | 缺点 |
|---|---|---|
| **whisper.cpp / WhisperKit**（本地） | 免费、离线、中文可用 | 模型 100–500MB；CPU 占用高（M 系列可用 Metal 加速） |
| **sherpa-onnx + Paraformer**（本地） | 中文效果好、体积小 | 需要额外模型下载 |
| **云端 ASR** | 不占 CPU | 要 API key；隐私（音频出本机） |

参考外部项目：`dsh-bili-watch`、`dsh-video-storyboard`、`video-understanding-kit` 都优先"官方字幕 → 本地转写 → 画面认字"的降级链。我们没有字幕轨，所以只剩"本地转写"这一级。

## 和看一阵时间线怎么对齐

- 音频按**块**处理（例如 10–30 秒一块）→ 每块产出带起止时间的转写；
- 段结算时，把**覆盖该段的转写**并进同一条时间线（与 OCR 文本并列，标来源 `asr`）；
- 拼图/画面仍是独立证据，模型需要时两者一起看；
- 记录里音频只留**转写文本**，音频原始文件用完即删（省磁盘、降隐私风险）。

## 成本估算（未验证）

- 本地 ASR：CPU 时间为主，50 分钟视频约等于实时或更慢（M 系列 Metal 加速可接近实时）；
- 云端 ASR：按分钟计费，50 分钟 ≈ 几元级，取决于供应商；
- 模型文本 token：转写文本约每分钟 200–300 字，比 OCR 更贵但信息量也更高。

## 隐私与交互

- 必须**显式开始/停止**，和屏幕录制同一套状态（气泡上显示"正在听"）；
- 默认关闭，首次开启要说明"会录下这台电脑正在播放的声音"；
- 录音只在本机转写，原始音频不落盘（或最多保留到转写完成）。

## 分阶段建议

1. **P1（低风险）**：先只做"硬字幕 OCR"优化——不新增权限，覆盖烧在画面里的字幕；这也是现在就能做的。
2. **P2**：ScreenCaptureKit 系统音频 + 本地 whisper.cpp，按块转写，接进时间线。
3. **P3**：CoreAudio 进程 tap，做到"只听这个应用"。

## 未决问题

- 转写粒度与段长如何对齐（按块转写，段结算时拼）？
- 是否需要"只说关键词"的轻量模式（关键词唤醒而不是全文转写）？
