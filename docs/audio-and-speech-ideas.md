# 「听」与「说」的设计留档（2026-11-07）

> 来源：对 [dsh-fish-buddy](https://github.com/Yuuyuko-uu/dsh-fish-buddy) 的调研。
> 本文件只做**留档与判断依据**，当前不排期。等「看」这条线稳定后再回来评估。

---

## 1. 它做了什么

| 能力 | 实现 | 关键细节 |
|---|---|---|
| **听 · 语音送话** | 本地 ASR（三档：228MB 通用 / 894MB 高精度 / 78MB 无标点），按住说话或电话模式 | 三档独立下载，选哪档下哪档；换档需重开会话才生效 |
| **听 · 陪看字幕** | 视频/直播每出一句**定稿字幕**就 `POST /hands/subtitle` 推给插件 | 插件按会话保留**最近 90 秒、最多 40 句** |
| **字幕注入方式** | 每轮用 `systemPrompt.context` **现拼**一段「【你正在看的】…」，**挂在消息尾部** | 不写进对话历史；不动系统提示词前缀 → 缓存不掉；无字幕时是空串 |
| **说 · 回话递回** | 那一轮回复完 → 回调挂件地址 → 挂件用气泡/弹幕显示 | 只递「挂件叫起来的那一轮」，你自己在 DSH 里聊的不推 |
| **说 · 随机搭话** | 每隔 N 分钟**掷骰子**，中了才开一轮让她说话 | 比「每 N 分钟必说」自然，也不累积欠账 |
| **说 · 游戏弹幕** | 她说的话横飞过屏 + 可锁定弹幕框 | 锁定后是真穿透（鼠标给到游戏） |

**它没有 TTS**：「说」是显示文字，不是读出来。

## 2. 两条可复用的工程结论

### 2.1 时间线/字幕应该「尾部注入」，不该进历史

原文：「挂在消息尾部，不动系统提示词的前缀，缓存才不掉」「不写进对话历史，所以不会越看越厚」。

对我们：任何「连续观测得到的上下文」（看一阵的时间线、OCR 文本）都应该走同一条路——
**外部状态 + 按需拼在尾部**，而不是写进会话历史或种子。

### 2.2 成本量级（它给出的实测）

> 一小时 111 次、每次约 60 万 token 上下文 → 几十块。

两个推论：
- 高频「每张都说」的模式很贵；
- **上下文越长，每轮越贵**（同一段上下文每轮重读）。所以「攒着、少说」才是默认。

## 3. 如果要给我们做「听」，需要决定什么

| 决策 | 选项 | 备注 |
|---|---|---|
| ASR 放哪 | 本地（whisper.cpp / SenseVoice） vs 云端 | 本地免费但要模型体积与 CPU；云端有成本与隐私 |
| 音频来源 | 系统音频（ScreenCaptureKit 可录） vs 麦克风 | 会议通常两者都要 |
| 触发方式 | 按住说话（短） vs 会话期间持续听（长） | 后者要显式状态指示与隐私提示 |
| 与「看」的关系 | 音频作为独立通道，按需拼接；还是与画面一起构成「看一阵」的一段 | 见下 |

## 4. 如果要给我们做「说」，需要决定什么

| 决策 | 选项 | 备注 |
|---|---|---|
| 输出面 | 已有气泡 / 输入面板 / 右键菜单 | 不需要新东西 |
| 语音输出（TTS） | macOS `say` / 云端 TTS / 不做 | `say` 免费但机械；云端自然但要花钱 |
| 主动开口 | 概率 + 间隔（学它） | 必须有总开关与频率上限 |

## 5. 我的判断（留档时的结论）

1. **「听」是会议场景的主干**：只抓画面会丢掉大部分信息。但它引入录音权限、模型体积、隐私问题，是一个独立模块。
2. **「说」的增量价值低**：我们现在没有 TTS，但气泡已经够用；加 TTS 属于体验升级，不是能力缺口。
3. **优先级**：先把「看」这条线（看一眼 → 短看 → 看一阵）做扎实；「听」作为 v2 候选，届时再决定本地还是云端。
4. 若将来做「听」，结构上应与「看」共享同一套**时间线 + 尾部注入**机制，而不是另起一套。
